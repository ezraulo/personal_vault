The incident

Nine minutes decided the outcome

The destruction and the accident that contained it happened inside the same ten-minute window. Times are from fseventsd and the saved terminal session.

19:07
Routine activity in the iCloud container

Book folders under ##BOOKSMB are touched. Unremarkable, but later mistaken for anomalous activity.

20:33
Recursive permission changes begin

Hours of chmod -R ug+rwx, chflags -R nohidden and dot_clean against the CloudDocs container, chasing a Nextcloud folder that refuses to delete.

21:44
Home directory still holds 165 entries

The last moment the folder is intact. Shortly after, sudo rm -rf /Users/august/.Trash/../ is issued.

21:51
Final iCloud filesystem event

The last Mobile Documents record in any log. After this the sync daemon has nothing left to observe.

21:53
The keychain dies — and saves everything

The login keychain is destroyed. macOS loses its iCloud credentials and signs the account out, severing sync before a single deletion can reach Apple's servers. An accident, and the reason this story has a good ending.

22:31
Home is down to ~22 entries

Desktop, Documents and Downloads are empty. A follow-up rm -rWv does nothing: -W undeletes whiteout entries, a concept that does not exist on APFS.

Sep 5
fseventsd recovered and parsed

2,438 log files covering the entire event, unbroken. 4.77 million filesystem records reconstruct the inventory that no other source held.

Evidence

How the missing inventory was reconstructed

No file-level record of the home folder existed. macOS keeps one anyway: fseventsd, the filesystem event log, which survived the deletion because it lives outside the home directory.

The logs also settled the question that resisted every other method: whether files had somehow been added to iCloud during the sign-out. They had not.

Created events on the 513 May-restore files ......... 0 Touched, metadata only ............................. 511 Last iCloud filesystem event ....................... 21:51 Account signed out ................................. 21:53 Events between those two timestamps ................ none

The files were always there. Their only events during the window were permission and extended-attribute changes at 20:33, 20:47 and 21:48 — the fingerprints of the operator's own recursive chmod runs. What changed was not the container but the method of looking at it: ls -le enumerates 746 loose root-level items that Finder makes easy to overlook.

Next

Sequence for getting back online

Order matters. The machine is currently signed out and cannot harm the cloud copy — the sync daemon's local database no longer exists, so it can pull but never delete.

Download the 87 from iCloud.com

No re-login required. The recovery map names the folder holding each file.

Request a full data export from Apple

Server-side archives delivered as download links, sized to fit an external drive. The Mac's sync state is never involved.

Repair permissions in place

8,085 world-writable paths remain from the recursive chmod runs. Tightening them is the inverse of the operation that caused the damage.

Sign in with Desktop & Documents sync off

That setting merges the local tree into the cloud rather than simply syncing it. Enable it only after a verified off-device copy exists.

Verify against the baseline

746 root items, 45 in Documents, 32 in Desktop, 18 in Downloads. If any count drops, sign out immediately.

Not recommended: a second local user account. iCloud provides one Desktop and Documents per Apple ID, not per user — two accounts merge into the same cloud folders, and macOS offers no supported way to merge home directories afterwards.

Method

Corrections made during the investigation

Four conclusions were reached, then overturned by better evidence. They are recorded because a forensic account that hides its own reversals is not trustworthy.

01

"Desktop & Documents sync was off." Inferred from the folders' absence in the legacy CloudDocs path. Wrong — since macOS 13 those sync roots live elsewhere. The web interface showed an exact match with the local structure.

02

"iCloud eviction explains the reappearing files." It does not. An evicted file still appears in ls — eviction removes content, not directory entries. The mechanism could not produce the observed effect.

03

"The 19:08 activity matches the rsync runs." A correlation asserted without checking. Those transfers targeted a different directory tree entirely.

04

"Normalise the extended attributes afterwards." Retracted. Recursive permission operations on a live sync container are precisely what preceded the loss, and the attributes were shown to be inert.
